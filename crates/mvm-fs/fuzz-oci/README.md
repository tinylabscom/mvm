# mvm-fs OCI unpack fuzz target

This standalone `cargo-fuzz` crate tests the OCI layer unpacker in `mvm-fs`.
Layer archives are untrusted registry input, so extraction must reject malformed
records and must never write outside the destination root.

## Who uses it

Contributors changing OCI archive parsing, whiteout handling, path validation,
or filesystem extraction run this target. The security workflow compiles and
periodically exercises it. The crate is fuzz infrastructure and is not part of
the runtime or published crate graph.

## How it works

The `unpack_layer` target writes each generated byte stream as a candidate
layer, creates a fresh temporary destination, and invokes the production
`mvm-fs` unpacking path. It then checks the two central invariants:

- arbitrary input never panics; and
- extraction never escapes the temporary destination through absolute paths,
  parent traversal, links, or malformed archive metadata.

A parser or validation error is an expected outcome. Successful extraction is
acceptable only when every produced path remains beneath the destination root.

## Running it

From this directory, with `cargo-fuzz` installed:

```bash
cargo +nightly fuzz run unpack_layer
```

Use `-- -max_total_time=300` for a five-minute local pass. Preserve useful
minimized artifacts as regression tests or corpus seeds.

## Workspace relationship

The root `Cargo.toml` excludes this package, and the manifest declares its own
empty `[workspace]`. This is necessary because `libfuzzer-sys` relies on the
sanitizer and linker configuration injected by the `cargo-fuzz` wrapper.
