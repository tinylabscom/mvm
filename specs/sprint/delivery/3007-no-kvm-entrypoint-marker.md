# 3007 — the hosted no-KVM witness refused its own fixture

`Hosted no-KVM bundle smoke (QEMU TCG)` has never passed. It was added in its
current form on 2026-09-04, and every run since has ended the same way:

```
[mvm] invoke: entrypoint invalid: canonicalize /bin/busybox sh -c 'exit 7': No such file or directory (os error 2)
::error::expected guest exit code 7 from installed bundle, got 1
```

The product was right and the fixture was wrong. `/etc/mvm/entrypoint` is a
marker, not a command line: `EntrypointPolicy::production()` resolves its
contents as an absolute path to a wrapper under `/usr/lib/mvm/wrappers/`, and
the only other shape the agent accepts is `sealed_script_marker()`, which takes
the marker file *itself* as the program when it begins with `#!` and carries
mode 0755 root:root on the same filesystem as `/etc/mvm`. A command line
satisfies neither, so the agent refused the entrypoint at boot exactly as it is
supposed to, and `machine run --entrypoint` returned 1.

There were two defects, not one. `debugfs write` creates its file **0644**, so
even a correct wrapper path would have been refused on mode. Both are fixed by
writing the shape mkGuest already bakes.

## Verified against the shipped bytes, not against the docstring

The release rootfs `boot-image/v0.1.3` was downloaded and read with `debugfs`.
Its marker is:

```
Inode: 417   Type: regular    Mode:  0755
User:     0   Group:     0                    Size: 257
#!/bin/sh
# Auto-generated by mkGuest at build time. Do not edit.
/nix/store/…-mvm-setpriv-…/bin/mvm-setpriv --reuid=1000 … -- /bin/sleep infinity
```

So the fixture now writes that same shape rather than inventing a third one.
The rewritten step was then extracted from the YAML and executed verbatim
against those release bytes on x86_64 Linux:

- marker lands at mode 0755, uid 0, gid 0;
- `stat -c %d` reports the same device for `/etc/mvm` and the marker;
- `veritysetup format` still produces a 64-character roothash over the edited
  image;
- and `chroot` into the mounted rootfs, running `/etc/mvm/entrypoint` in the
  image's own userspace, **exits 7**.

That covers every condition `sealed_script_marker()` checks plus the exit code
the lane asserts. What it does not cover is the boot itself, which the lane's
own dispatch answers.

## The assertion that matters runs on pull requests

The lane is nightly, so it took a full cycle per attempt to learn anything, and
the only thing checking the marker was a guest three jobs downstream. Two
guards now sit earlier:

- the fixture step asserts its own output — mode, ownership, and the shebang —
  and fails at assembly time with the offending `stat` in the message;
- `no_kvm_pipeline_prepares_a_bounded_bundle_then_boots_with_tcg` pins the
  shebang line and the `sif … mode 0100755` call, so reverting to a command
  line fails on **every PR** rather than on a nightly nobody reads.

The second assertion was confirmed to fail against the old fixture before being
kept.

## Not done

`entrypointArgv` in the sidecar stays `["/bin/busybox", "sh", "-c", "exit 7"]`.
That remains true of what runs — the marker `exec`s exactly that — and it is
inert for this lane, which passes no `--stdin`, so nothing reads it.

The two other Extended CI failures in #3007 (the image's declared `PATH` not
reaching a run, and the SDK live scenario's arch-mismatched image pin) are not
touched here; they are separately owned and land on their own.
