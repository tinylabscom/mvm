# MVM packs

Backing: preview
Validation: none

This is the design attachment for #3716. ADR-055 owns the naming and trust
decisions. The issue owns delivery status and acceptance evidence. The design
describes the target; the existing registry-pack implementation is a smaller
policy-and-image-source subset, not a completed official pack system.

## Product boundary

A pack is an immutable, versioned workload distribution: a prepared machine
environment, zero or more applications, and an explicit MVM policy, with
optional task content. `mvm/claude` and `mvm/codex` must include a usable
application and policy without task data; `mvm/datascience` may include several
applications. A template generates project files and can refer to a pack, but
is not an installed workload. An image set supplies MVM's verified Linux
base, builder and current guest-runtime components; a pack supplies a workload
on a compatible base set. A snapshot or checkpoint captures one machine's
mutable state, not a release. A `.mvmpkg` transports a particular machine and
its posture; it may record an installed pack's identity but is not the pack's
publisher namespace. An OCI image may be an input or application payload; it
does not declare MVM policy, entrypoints, task evidence or MVM publisher trust.

The CLI's user-facing `pack` family should own workload distribution. The
existing attested builder/runtime/image-project cache remains a distinct
internal artifact family and moves behind an explicit `pack system` surface,
with old commands retained as compatibility aliases for one release. The
extension-pack protocol remains an extension mechanism, never an alias for a
workload pack. `registry_pack` names can remain as internal migration seams
until callers are updated; the public term is simply “pack.”

## Signed artifact

Each versioned pack has one canonical manifest, a detached signature bundle,
and a closed set of payload files. Its reference is
`publisher/name@major.minor.patch`; `mvm/` is reserved. The manifest declares
schema version, reference, description, publisher, supported host and guest
architectures, compatible base-set tag and digest, dependencies pinned to
exact reference and manifest digest, application IDs and versions, payload
paths and digests, entrypoints, policy path and schema, optional image
descriptor, optional task descriptors, provenance and license metadata. Each
application declares its in-guest executable or service endpoint, launch
arguments, required files, and the subset of pack policy it requests. An
installable payload is either included with a digest or named by an immutable
digest and reproducibly resolved before installation; no launch performs an
implicit software download.

The signature authenticates the exact manifest bytes. The manifest lists
every payload file by safe relative path, size and SHA-256 digest, including
policy, application binaries or installable payloads, image, launch wiring,
task specifications, data, scripts and verification artifacts. Verification
rejects extra paths, links, path traversal, duplicate names, changed bytes or
missing members. The detached signature bundle is not a payload member. A
built image has its own digest in the descriptor; source `flake.lock` and
source-file digests are build inputs, not a substitute for the output digest.
Where a payload is external, the descriptor pins its content digest and
signed provenance, and pull materializes and verifies it before install.
Opaque mutable URLs are forbidden. No secrets or credential values belong in
the manifest, image or payload.

## Publisher trust and status

Built-in trust reserves `mvm/` for an MVM-controlled release workflow identity
and an exact issuer; no wildcard grants official status. A verified pack is
labelled official only if the entire manifest, every payload, release identity,
and current revocation state validate for that namespace. Search results and
unsigned indexes are hints; their labels cannot establish trust. Other
publishers may use their own namespaces under an explicit operator trust
policy and are always distinguished from MVM official packs. An unsigned or
untrusted artifact can be inspected offline as untrusted data but cannot be
installed or run through the official path. A signature proves publisher and
integrity, not safety.

The project publishes a signed trust-root document with monotonically
increasing version, accepted workflow identities and validity intervals,
revoked identities and manifest digests, and an expiry. A release embeds a
root key or equivalent trust anchor; the root signing key is held outside pack
CI and used only for trust-root and revocation releases. Pack CI obtains
short-lived signing credentials through its restricted publish workflow and
cannot edit the trust root. Rotation overlaps old and new identities only for
an announced, bounded interval, with exact namespace, issuer and effective
dates. The verifier returns the authenticated identity rather than a boolean
so revocation applies to the signer that actually signed the manifest.
Previously installed packs are rechecked at execution against current
trust and revocation data. A stale, missing, malformed, expired or
unreachable revocation document fails closed for official install and run;
an offline operator must supply a still-valid signed document. Rollback of the
trust document is refused. Revoking an identity or manifest digest blocks
both new pulls and cached execution, including old lock entries.

The repository rename changes the workflow identity. Keep the old identity
only for already published references through a dated migration window, or
re-sign and re-publish those bytes under the new identity. Do not silently
extend trust to the new identity or depend on repository URL redirects.
`mvm/` publication begins only after the new identity and revocation path are
verified. Existing `agent/` and `runtime/` lock entries remain exact legacy
references; an explicit migration command or guide pulls the replacement,
reviews policy changes, and updates the lock. Reference aliases do not confer
official status.

The migration has five breaking edges: the repository URL and release workflow
identity; `agent/` and `runtime/` references in commands, policy includes and
lockfiles; the public `pack registry` verbs moving to `pack`; the old
attested-cache `pack` verbs moving to `pack system`; and unsigned templates
becoming pack-aware scaffolds. Keep legacy command spellings and exact old
pins working during the announced transition. Never rewrite a lockfile or
policy include without showing the replacement reference and its grants.
Document the cutoff and test redirects separately, but use explicit old and
new URLs rather than relying on redirects for artifact or trust resolution.

## Policy and execution

The signed policy is a versioned MVM policy document, stored as a declared
payload. It covers filesystem shares, network destinations and egress,
capabilities, tools, secrets bindings and resource ceilings. Inspection shows
the pack policy, the application request, its provenance, and the proposed
effective grants before execution. The effective policy is the intersection
of pack policy, application request, invocation grants, user policy and host
constraints; denies and tighter bounds prevail. Omitted fields grant nothing.
The application cannot request more than its pack declares, and task content
cannot add policy. Pack layers cannot add host shares or escape hatches.
Pack-declared secret names and destinations are requests only: the CLI names
the stored secret and its destination in the approval view, and an invocation
must explicitly authorize each binding. Values enter only through the
supported runtime secret channel. The signed `ExecutionPlan` carries the
manifest digest, application identity, payload digest and effective grants;
host admission re-verifies the artifact and plan, and decisions enter the
chain-signed audit log. Workloads remain inside the microVM, with no guest
NIC or TAP/TUN and vsock as the host channel.

Applications are launched by stable, signed IDs and entrypoint records, not
by host path substitution. An update selects a new exact pack version and
manifest digest, displays changed payloads and policy, verifies it, then
atomically changes the lock. Running processes keep their admitted version;
rollback is another verified lock selection. Failure to verify any digest,
identity, revocation state or effective-policy bound refuses the launch.

## Optional task environments

A pack may declare one or more repeatable tasks, each with a starting state,
goals, inputs, expected outputs and constraints. Signed members may contain
setup scripts, datasets, fixtures, annotations, reference trajectories, state
extractors, integrity checks and weighted checklists. Every dataset and
reference artifact declares a license and provenance. A task can span
multiple applications. Task content is untrusted input even when integrity
verified; scripts execute only inside the pack's existing boundary and grants.
Outcome verification is evidence about a task, not proof the environment is
safe. Ordinary application packs need no task content.

## Local workflow and release order

`mvmctl pack search` discovers; `pack info` displays manifest, signer,
revocation freshness, applications, policy and payload digests; `pack verify`
checks all members; `pack pull` verifies and atomically pins; `pack run
mvm/name@version --app id -- ...` verifies again, previews the effective
grants and runs an admitted plan. Existing `search`, `pull`, `run --policy` and
`pack registry` forms remain compatibility paths during migration. The
first release can use a static HTTPS index plus content-addressed objects and
an offline file mirror. A later registry must provide immutable versioned
objects, digest-addressed download, publisher namespace control, signed
revocation/trust-root distribution, pagination, and atomic index publication;
its index is not a trust root.

The smallest useful release is one published `mvm/` application pack with a
prepared image, signed policy and entrypoint, built on the pinned base set,
reproduced, signed and attested by pack CI, then verified, inspected, pulled
and run through signed admission with an end-to-end vsock-only witness. Ship
the default official trust root, revocation enforcement, cache re-verification,
and honest CLI status in that slice. Keep the existing category packs as
legacy policy packs until migrated. Defer a hosted registry, community
publishing automation, optional task artifacts, multi-application orchestration
and automatic updates. Do not claim the image build or provenance guarantee
until its producer and consumer checks are running in CI.
