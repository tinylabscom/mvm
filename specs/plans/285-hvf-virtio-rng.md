# HVF virtio-rng

**Status:** In progress.

**Issue:** [#2060](https://github.com/tinylabscom/mvm/issues/2060)

**Goal:** Give every guest booted by the portable HVF VMM a continuously
replenished entropy source without weakening the per-boot `/chosen/rng-seed`
that covers the window before the guest driver probes.

## Security and lifecycle invariants

- Host entropy comes directly from the operating-system CSPRNG. An unavailable
  source fails closed: the device does not complete or consume the request.
- Guest-controlled queue geometry, descriptor directions, addresses, and sizes
  are validated and bounded before host work or guest-memory writes.
- Generated bytes are written directly to the current guest request and are
  never buffered in serializable device state, so pause/resume and restoration
  cannot replay an old entropy block.
- `/chosen/rng-seed` remains mandatory and fresh for every boot.

      reset-safe device cursors.
- [x] Cover identity negotiation, successful fills, successive non-repeating
      requests, early and mid-generation host entropy failure, per-notification

- [x] Boot the current branch on macOS HVF and prove Linux binds `virtio_rng`,
      exposes `/dev/hwrng`, and serves repeated entropy reads after startup.
- [ ] Run formatting, focused tests, workspace tests/check, all-target Clippy,

- [ ] Queue and merge the pull request, synchronize `main`, close #2060, and

Live evidence (2026-08-02): an Alpine 3.20 workload booted through the signed
HVF supervisor on macOS 26.5.2. The guest reported `virtio_rng.0` in
`rng_available`, `/dev/hwrng` was a character device, and two successive
2,048-byte reads completed with distinct SHA-256 digests. The one-shot VM then
exited and was torn down normally.
